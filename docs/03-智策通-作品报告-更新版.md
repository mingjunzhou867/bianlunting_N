# 智策通——基于大模型的多Agent辩论与证据链取证研判系统

**2026年（第19届）中国大学生计算机设计大赛 人工智能实践赛 作品报告**

---

## 摘要

政策审查是政务服务中的关键环节，传统人工审核模式面临效率低、标准不一、证据追溯困难等痛点。本作品"智策通"是一个面向政策审查场景的多Agent智能研判系统，以大语言模型为核心驱动，通过可插拔的政策包与数据源抽象架构、规则驱动的Text-to-SQL证据链取证机制、面向执行反馈的SQL自诊断修复机制、形式化论证框架驱动的多Agent辩论机制、以及三层级联决策引擎与人工复核留痕五大创新，实现了从自然语言提问到结构化证据采集、多角色辩论研判、可信决策输出的全链路自动化。

系统以灵活就业社保补贴资格认定为典型案例，采用MySQL数据库存储参保、缴费、就业登记等多源数据，通过5个具有不同认知视角的辩论Agent进行结构化对抗论证，结合Dung抽象论证框架与ASPIC+攻击类型映射，实现了论证状态的形式化计算与动态收敛。实验表明，SQL自诊断修复机制将查询结果匹配率从65.00%提升至87.50%（+22.50个百分点），完整多Agent辩论决策质量达91.04%，证据引用率达84.72%。

**关键词：** 大语言模型；多Agent辩论；Text-to-SQL；论证框架；可插拔架构；政策审查；证据链

## 第1章 作品概述

### 1.1 背景与动机

政策审查是政府公共服务中的核心业务之一。以灵活就业社保补贴为例，申请人需满足多项条件（就业困难人员认定、灵活就业登记、社保缴费状态等），审核人员需跨多个业务系统调取数据、逐条比对政策规则、综合判断资格。这一过程存在以下突出问题：

1. **效率瓶颈**：人工逐条查询、比对、记录，单次审核耗时长，难以应对大规模集中申报。
2. **标准不一**：不同审核人员对同一政策条款的理解和执行存在差异，导致"同案不同判"。
3. **证据追溯困难**：审核过程缺乏结构化记录，事后复查难以还原决策依据。
4. **政策适应性差**：系统硬编码政策规则，新政策上线需大量开发工作，无法快速响应政策变化。
5. **论证过程不透明**：传统系统仅输出结论，无法展示推理链条和争议焦点，不利于监督问责。

大语言模型（LLM）在自然语言理解、代码生成、逻辑推理等方面展现出强大能力，为构建智能化政策审查系统提供了新的技术路径。然而，单一LLM调用存在"幻觉"、推理不一致、缺乏可解释性等问题，难以直接应用于高stakes的政策决策场景。

### 1.2 作品定位

本作品定位为**面向政策审查场景的多Agent智能研判系统**，核心设计理念是：

- **证据驱动**：所有决策必须基于结构化证据，禁止"无证据推理"；
- **对抗论证**：通过多角色辩论发现推理漏洞，避免单一视角偏见；
- **形式化可计算**：引入论证框架理论，将主观论证转化为可计算的攻击-防守关系；
- **可插拔扩展**：政策规则和数据源均通过YAML配置声明，核心引擎与业务逻辑解耦。

### 1.3 主要创新点

本作品包含以下五个创新点：

**创新点一：可插拔政策包与数据源抽象架构。** 设计Policy Pack和Data Source Pack双层插件体系，通过YAML声明式配置实现政策规则、数据源映射、采集器注册的完全解耦，新增政策或数据源无需修改核心引擎代码。

**创新点二：规则驱动的Text-to-SQL证据链取证机制。** 构建五层证据链流水线（Evidence Planner → Text2SQL Agent → Prompt Builder → Evidence Assembler → Hard Rule Semantics），将政策规则自动转化为结构化查询，实现"规则→SQL→证据→结论"的端到端自动化。

**创新点三：面向执行反馈的SQL自诊断修复机制。** 设计包含查询结果校验、错误模式识别、反馈式重试的三层修复流水线，将SQL查询首次执行匹配率从65.00%提升至87.50%，结构性警告率从32.50%降至7.50%。

**创新点四：形式化论证框架驱动的多Agent辩论机制。** 引入Dung抽象论证框架（1995）和ASPIC+攻击类型映射，设计5个具有不同认知视角的辩论Agent，通过客观冲突检测、举证责任三级分层、Grounded Semantics可接受集合计算，实现论证状态的形式化判定与动态收敛。

**创新点五：三层级联决策引擎与人工复核留痕。** 设计"确定性规则引擎 → 加权投票 → 多数决兜底"三层级联决策流水线，结合ConservativeArbiter反事实推演，实现决策结果的可解释性和人工复核的完整留痕。

### 1.4 关键词

大语言模型；多Agent辩论；Text-to-SQL；论证框架；可插拔架构；政策审查；证据链

## 第2章 问题分析

### 2.1 政策审查业务分析

政策审查的本质是一个**条件匹配与证据验证**过程。以灵活就业社保补贴为例，审查流程包括：

1. **身份确认**：核实申请人是否为就业困难人员；
2. **就业状态核查**：确认是否以灵活就业形式实现就业并登记；
3. **社保缴费核查**：确认是否以个人身份缴纳社会保险费；
4. **排除条件排查**：核查是否存在不宜享受补贴的风险情形（如跨单位重复缴费、缴费基数异常等）；
5. **补贴月数计算**：根据缴费记录计算应补贴月数。

这一流程涉及多个数据源（就业登记系统、社保缴费系统、困难人员认定系统）、多种规则类型（必须满足的准入条件、必须排除的风险条件、灵活评判的辅助条件）、以及复杂的推理逻辑（条件组合、时序关系、异常检测）。

### 2.2 核心技术挑战

本作品需要解决以下核心技术挑战：

**挑战一：泛用性与可扩展性。** 传统系统将政策规则硬编码在业务逻辑中，新增政策需要修改核心代码。本作品需要设计一种声明式配置机制，使政策规则、数据源映射、采集策略均可通过配置文件定义，核心引擎保持政策无关性。

**挑战二：自然语言到结构化查询的转化。** 政策规则以自然语言描述，但数据查询需要结构化SQL。本作品需要构建一个从政策规则到SQL语句的自动转化管线，同时处理表名映射、字段约束、枚举值转换、安全脱敏等工程细节。

**挑战三：查询结果的语义理解。** SQL查询返回的是原始数据行，需要转化为具有业务含义的证据结论（支持/反对/中性）。本作品需要设计一个证据组装器，将原始查询结果转化为结构化的证据条目，并通过硬规则语义覆盖确保关键判断的确定性。

**挑战四：SQL生成的可靠性。** LLM生成的SQL可能存在语法错误、字段幻觉、逻辑偏差等问题。本作品需要设计一个自诊断修复机制，通过执行反馈、错误模式识别、约束校验等手段提升SQL生成的可靠性。

**挑战五：多视角决策的一致性。** 政策审查涉及严格合规与灵活服务之间的张力。本作品需要设计一个多Agent辩论机制，通过结构化对抗发现推理漏洞，同时引入形式化论证框架确保辩论过程的可计算性和可解释性。

**挑战六：决策结果的可信性。** 单一决策方法可能存在盲区。本作品需要设计一个级联决策引擎，通过规则引擎、加权投票、多数决三层互补，确保决策结果的鲁棒性，并在存在冲突时自动标记人工复核需求。

### 2.3 技术路线选择

针对上述挑战，本作品采用以下技术路线：

| 挑战 | 技术方案 | 理论基础 |
|------|---------|---------|
| 泛用性 | YAML声明式配置 + 插件注册表模式 | 策略模式、依赖注入 |
| NL2SQL | 约束Prompt + 白名单字段 + DDL注入 | Few-shot CoT、Schema Linking |
| 语义理解 | LLM组装 + 硬规则语义覆盖 | 确定性规则优先原则 |
| SQL可靠性 | 错误反馈循环 + 结构化守卫 | Self-Refine、Constrained Decoding |
| 多视角辩论 | 5-Agent对抗 + 形式化论证框架 | Dung AF (1995)、ASPIC+ (Walton 2008) |
| 可信决策 | 三层级联 + 反事实推演 | 集成学习、因果推理 |

### 3.2 可插拔配置层设计（创新点一）

#### 3.2.1 设计动机

传统政策审查系统将规则硬编码在业务逻辑中，导致：
- 新政策上线需要修改核心代码，开发周期长；
- 政策规则与数据源紧耦合，更换数据库需要重写查询逻辑；
- 不同政策的特殊处理逻辑散布在各处，难以统一管理。

#### 3.2.2 Policy Pack架构

Policy Pack是政策规则的自包含配置单元，每个政策对应一个独立目录，包含6个YAML配置文件：

```
policy_packs/
└── flexible_employment_subsidy/
    ├── manifest.yaml           # 策略身份元数据
    ├── rules.yaml              # 结构化规则定义
    ├── evidence_requirements.yaml  # 取证需求映射
    ├── prompts.yaml            # 策略专用Prompt模板
    ├── report_template.yaml    # 裁决报告格式
    └── collector_overrides.yaml # 采集器覆盖配置
```

**manifest.yaml** 定义策略身份信息，包括pack_id、policy_id、policy_name、policy_type、version、default_data_source_id、keywords、intent_patterns、decision_labels、task_header、policy_scope等字段。系统通过manifest实现策略路由——用户输入自然语言问题后，Intent Agent根据keywords和intent_patterns自动匹配最相关的Policy Pack。

**rules.yaml** 将政策条文结构化为四个规则桶：
- `basic_conditions`（必须满足条件）：如"已认定为就业困难人员"、"已实现灵活就业并登记"、"已以个人身份缴纳社保"；
- `exclusion_conditions`（必须排除条件）：如"不存在跨单位重复缴费"、"不存在缴费基数异常"；
- `inference_rules`（推理规则）：用于辅助判断的逻辑推导；
- `calculation_rules`（计算规则）：如"补贴月数 = 连续缴费月数"。

每条规则包含rule_id、description、sql_template_ref、allowed_fields、evidence_targets、notes_for_query_generation、no_data_summary、no_data_supports、assembler_guidance等字段，为下游各环节提供完整的上下文信息。

**evidence_requirements.yaml** 建立规则到数据实体的映射关系，定义每条规则需要查询的实体、字段、期望信号和降级策略。

**prompts.yaml** 存放策略专用的Prompt模板，避免在代码中硬编码提示词。

**report_template.yaml** 定义裁决报告的格式模板，支持按策略定制报告样式。

**collector_overrides.yaml** 为特定规则配置采集器的覆盖行为，包括作用域校验器、恢复策略、波动性分析器等。

#### 3.2.3 Data Source Pack架构

Data Source Pack是数据源的自包含配置单元，每个数据源对应一个独立目录：

```
data_source_packs/
├── local_mysql_demo/
│   ├── manifest.yaml       # 数据源类型、连接信息
│   ├── schema_map.yaml     # 逻辑实体→物理表映射
│   └── collectors.yaml     # 声明可用的采集器
└── table_payload_demo/
    ├── manifest.yaml       # 类型=table_payload，无需数据库
    └── collectors.yaml     # 声明TablePayload采集器
```

**schema_map.yaml** 实现逻辑实体到物理表的字段级映射。例如，逻辑实体"person"映射到物理表`sys_user_info`，逻辑字段`id_card`映射到物理字段`sfzh`（身份证号），逻辑字段`name`映射到物理字段`xm`（姓名）。这种映射机制使得Policy Pack中的规则可以使用统一的逻辑实体名，而无需关心底层数据库的实际表结构。

#### 3.2.4 Collector Registry机制

采集器注册表（CollectorRegistry）实现数据源类型到采集器工厂的动态映射。系统预注册了两种采集器：
- `DynamicEvidenceCollector`：面向MySQL数据源，通过Text2SQL自动生成查询；
- `TablePayloadCollector`：面向API提供的表格数据，直接解析无需数据库查询。

新增数据源类型只需实现EvidenceCollectorProtocol接口并注册到Registry，无需修改任何现有代码。

#### 3.2.5 三方解耦的关键设计

Policy Pack、Data Source Pack和Collector三方解耦的核心设计原则是：

- **Policy Pack声明"取什么"**：规则和证据需求定义了需要采集的信息；
- **Data Source Pack声明"从哪取"**：schema_map定义了数据的物理存储位置；
- **Collector决定"怎么取"**：采集器根据数据源类型选择合适的查询策略。

这种三方分离使得新增政策或数据源无需修改核心引擎代码，只需添加配置目录和（可选的）新采集器实现。

### 3.3 规则驱动的Text-to-SQL证据链（创新点二）

#### 3.3.1 五层证据链架构

证据链采用五层流水线设计，每层职责明确、可独立测试：

**第一层：Evidence Planner（证据规划器）**

Evidence Planner是证据链的起点。输入申请人ID和策略ID，输出有序的EvidencePlan。规划器首先尝试从Policy Pack加载规则（`_build_plan_items_from_policy_pack`），读取四个规则桶的全部规则和evidence_requirements。每条规则转化为一个EvidencePlanItem，携带rule_id、rule_type、sql_template、priority、allowed_fields、evidence_targets、notes_for_query_generation、expected_answer_shape、missing_evidence_strategy等元数据。规划器按优先级排序：basic_conditions（rank 0）最先执行，exclusion_conditions（rank 1）次之，inference_rules和calculation_rules（rank 2-3）最后执行。这确保了关键准入条件优先验证，避免在不满足基本条件时浪费后续计算资源。

**第二层：Text2SQL Agent（文本转SQL代理）**

Text2SQL Agent接收EvidencePlanItem和申请人ID，生成可执行的SQL语句。如果PlanItem已携带sql_template（来自Policy Pack配置），则直接返回模板，无需调用LLM。否则，通过QueryPromptBuilder构建约束性Prompt，调用LLM（temperature=0.1）生成SQL。模板优先策略显著减少了LLM调用次数，提升了查询的确定性和效率。

**第三层：Query Prompt Builder（查询提示构建器）**

Query Prompt Builder构建高度约束的系统提示，包含：
- 目标表DDL（仅包含当前规则所需的表）；
- 数据字典摘录（枚举值映射，如insurer_status='101'表示单位缴费，'102'表示灵活就业）；
- 字段白名单（来自PlanItem的allowed_fields）；
- 规则特定备注（如明细查询规则不得使用COUNT(*)）；
- 安全脱敏占位符（id_card_replace替代真实身份证号）；
- MySQL 8.0语法约束。

DDLManager类解析schema_struct.sql文件，按表名提取CREATE TABLE语句。DictManager加载JSON数据字典文件，提供枚举值映射。这种约束性Prompt设计将LLM的生成空间限制在合法范围内，显著降低了SQL错误率。

**第四层：Evidence Assembler（证据组装器）**

SQL执行后，Evidence Assembler将原始数据行转化为带业务含义的自然语言摘要。组装器使用LLM调用（温度0.2），结合规则特定的assembler_guidance字段（来自Policy Pack），输出结构化JSON：包含result_summary（自然语言描述）和supports_conclusion（布尔值，表示该证据是否支持规则通过）。例如，P001_FLEX_004规则的guidance说明："此为风险预警条款，非否决条件；若缴费基数稳定，supports_conclusion应为null。"

**第五层：Hard Rule Semantics（硬规则语义覆盖）**

在组装器输出后，确定性的硬规则语义覆盖LLM的判断：
- MUST规则：查询返回有效数据（非COUNT=0）→ supports_conclusion=True；否则False；
- EXCLUDE规则：查询返回有效数据 → supports_conclusion=False（发现风险）；否则True（无风险）。

这一机制确保即使LLM组装器出现判断偏差，关键的准入和排除条件仍由确定性规则保证正确性。

#### 3.3.2 证据模型

每条证据（EvidenceItem）包含：evidence_id、rule_id、target_id_card、target、category、sql、result_raw、result_summary、supports_conclusion、confidence、exec_status、diagnostic_code/label/detail/hint、manual_verified、manual_stance等字段。EvidenceBundle将同一申请人的所有证据条目分组，提供by_rule查找接口。

证据诊断函数classify_evidence_diagnostic()将执行状态和错误信息映射为诊断代码（ok、empty_result、missing_column、missing_table、table_corrupted、sql_error、db_connection_error、query_error、unknown_error），附带人类可读的标签和排障提示。

### 3.4 SQL自诊断修复机制（创新点三）

#### 3.4.1 问题背景

LLM生成的SQL存在三类典型错误：
1. **语法错误**：窗口函数别名在同一层级WHERE/HAVING中引用、GROUP BY缺失等；
2. **字段幻觉**：引用不存在的列名（如`hc.valid_from`、`hc.status`）；
3. **逻辑偏差**：不当添加过滤条件（如在未要求时添加`is_valid='1'`）。

首次执行匹配率仅65.00%，结构性警告率高达32.50%，严重影响证据链的可靠性。

#### 3.4.2 三层修复流水线

AutoDebugger类封装Text2SQL Agent，构建最多3次重试的修复循环：

**第一层：生成与安全替换。** 调用Text2SQLAgent.generate_sql()生成SQL，然后将id_card_replace占位符替换为实际身份证号。若为重试，将上次错误信息作为error_feedback传入LLM。

**第二层：结构化守卫（Detail Query Guardrail）。** 对标记为明细查询的规则（如P001_MUST_003、P001_FLEX_002、P001_FLEX_004、P001_FLEX_005），执行三项校验：
- 拒绝聚合查询（COUNT、EXISTS）——明细查询必须返回字段级事实；
- 拒绝幻觉列名——SQL中的列名必须在allowed_fields白名单中；
- 检查列名与schema的一致性。

**第三层：错误反馈循环。** 若SQL执行抛出SQLAlchemyError，错误信息被捕获并传递给下一次LLM调用。Prompt Builder内置针对性修复提示：
- 枚举值错误："insurer_status只能是'101'或'102'，不能是'101单位缴费'";
- 窗口函数错误："不能在同一层级WHERE/HAVING中引用窗口函数别名，应使用子查询或CTE";
- 过滤条件错误："仅在问题明确要求有效记录时才添加is_valid='1'"。

#### 3.4.3 实验效果

| 指标 | 无修复 | 有修复 | 提升 |
|------|--------|--------|------|
| 最终匹配率 | 65.00% | 87.50% | +22.50pp |
| 结构性警告率 | 32.50% | 7.50% | -25.00pp |

修复机制将SQL查询的可靠性提升至可用水平，为后续多Agent辩论提供了高质量的证据基础。

### 3.5 形式化论证框架驱动的多Agent辩论（创新点四）

#### 3.5.1 设计动机

传统多Agent系统采用简单的"投票聚合"方式整合各Agent判断，存在以下问题：
- 缺乏论证过程的结构化记录，无法追溯"为什么这个判断胜出"；
- Agent自报攻击目标不可靠，需要客观冲突检测机制；
- 缺乏形式化的论证状态计算，辩论收敛依赖经验值；
- 不同规则类型应适用不同的举证标准，而非统一阈值。

#### 3.5.2 五角色辩论Agent设计

系统设计5个具有不同认知视角的辩论Agent：

**StrictComplianceAgent（严格合规Agent，temp=0.1）：** 硬约束视角。对缺失数据持保守态度——必须满足条件未确认即视为不满足；必须排除条件未发现即视为无风险（而非"缺失"）。适合作为合规底线的守护者。

**LenientBusinessAgent（宽松业务Agent，temp=0.3）：** 服务导向视角。允许非关键缺失项的灵活性——若正面证据充分且无排除条件触发，可通过。适合体现政务服务的人性化。

**ExploratoryAgent（探索分析Agent，temp=0.45）：** 差距与异常检测视角。识别证据间的矛盾、不确定性的来源和系统性盲区。适合发现其他Agent可能忽视的问题。

**EmpiricalReasoningAgent（经验推理Agent，temp=0.3）：** 基于案例的推理。通过empirical_case_retriever检索相似历史案例，比较当前证据模式，必须在推理中引用CASE_X。适合提供先例参考。

**AuditChallengeAgent（审计挑战Agent，temp=0.2）：** 反向审计视角。挑战乐观推理，对"看起来通过"的证据链进行反向审查。适合防止过度乐观的误判。

#### 3.5.3 Dung抽象论证框架实现

ArgumentGraph类实现基于Dung（1995）的抽象论证框架：

**Argument数据结构：** 每个论证携带arg_id、text、source_agent、round_num、evidence_refs、stance（PASS/REJECT/INSUFFICIENT）、confidence（客观计算）、attacks、supported_by、proof_standard、status（active/defeated/undecided）。

**ASPIC+攻击类型映射：** 系统定义5种攻击类型，采用ASPIC+术语体系：
- REBUTTAL（结论反驳，weight=0.9）：相同证据，相反结论；
- DEFEATER（立场对立，weight=0.7）：矛盾的立场判断；
- UNDERCUT（推理质疑，weight=0.5）：攻击推理链条；
- UNDERMINING（证据削弱，weight=0.6）：攻击证据前提；
- POLICY_MISMATCH（条款误用，weight=0.8）：错误引用政策条款。

**Grounded Semantics可接受集合计算：** 采用迭代不动点算法。初始时，无攻击者的论证被标记为acceptable。然后迭代：若某论证的所有攻击者都已被defeated，则该论证被标记为acceptable。攻击者defeat目标的条件是：`attack.weight × attacker.confidence ≥ proof_standard_threshold × target.confidence`。proof_standard_threshold来自规则类型的举证标准映射。

**动态终止机制：** 调度器在每轮辩论后检查可接受集合是否稳定——若连续两轮的acceptable set不变，则辩论提前结束，避免不必要的LLM调用。

#### 3.5.4 举证责任三级分层

系统将规则类型映射到法律举证标准：

| 规则类型 | 举证标准 | 阈值 | 法律含义 |
|---------|---------|------|---------|
| 必须满足（basic_conditions） | 优势证据（Preponderance） | 0.50 | 较低通过门槛 |
| 必须排除（exclusion_conditions） | 排除合理怀疑（Beyond Reasonable Doubt） | 0.90 | 较高排除门槛 |
| 灵活评判（inference/calculation） | 清晰且有说服力（Clear and Convincing） | 0.70 | 中等标准 |

这种分层设计使得不同类型规则的判断阈值与其业务语义一致：准入条件不应过于严苛（避免"因噎废食"），排除条件必须高确信度（避免"误伤无辜"）。

#### 3.5.5 客观冲突检测（AttackDetector）

AttackDetector不信任Agent自报的攻击目标，而是客观检测四类冲突：

- **证据冲突**：同一证据被不同Agent引用但得出相反结论；
- **立场冲突**：PASS vs REJECT，根据confidence确定方向；
- **逻辑缺陷**：论证依赖标记为missing/unresolved的证据；
- **数据缺失**：从缺失证据中得出确定性结论。

冲突检测结果以结构化摘要（conflict_summary）注入后续轮次的Agent提示，确保Agent必须回应具体的争议点而非泛泛而谈。

#### 3.5.6 辩论调度流程

DebateOrchestrator._execute_debate()执行以下流程：

1. **第0轮**：5个Agent并行判断（ThreadPoolExecutor，max_workers=5）。论证提取到ArgumentGraph。AttackDetector发现冲突。
2. **第1..N轮**：Agent接收conflict_summary和round_summaries，必须回应具体冲突点。论证重新提取，冲突重新检测。动态终止检查。
3. **终结**：ArgumentGraph.finalize_arguments()标记所有论证为accepted/defeated/undecided。
4. **仲裁**：ConservativeArbiter解释多数结果（不修改结果），生成反事实推演。
5. **报告**：构建AdjudicationReport，包含条款级结果。

### 3.6 三层级联决策引擎（创新点五）

#### 3.6.1 三层决策流水线

unified_decision_engine.decide()函数实现三层级联决策：

**第一层：确定性规则引擎（Rule Engine）。** run_rule_engine()函数检查证据项与结构化规则的匹配关系。对每条规则，check_rule_against_evidence()使用decision_semantics.build_item_semantics()判断证据的语义效果（支持/反对/中性）。关键机制：
- **一票否决**：任一basic_conditions规则失败 → pre_decision="FAIL"，confidence=0.95，直接跳过第2、3层；
- **一票通过**：所有basic_conditions通过 且 无exclusion失败 且 无missing/unknown证据 → pre_decision="PASS"（仍运行第2、3层验证置信度）；
- 若两者都不满足 → pre_decision=None（需要辩论）。

**第二层：加权投票（Weighted Vote）。** aggregate_weighted_stances()函数计算加权支持/反对/待定分数。每个Agent的权重 = `agent_confidence × 0.6 + evidence_quality × 0.4`。evidence_quality是引用证据卡的平均分（0-100）。权重下限0.1，防止零权重。主导立场为权重总和最高的立场。支持票需超过阈值（默认0.6，按举证标准调整：0.5/0.7/0.9）。

若第1层说PASS但第2层说FAIL，结果为FAIL且`requires_human_review=True`（检测到冲突）。

**第三层：多数决兜底（Majority Fallback）。** 简单多数投票：统计PASS/FAIL/MISSING。严格多数（>50%） required。若无多数，返回MISSING且`requires_human_review=True`。

#### 3.6.2 决策语义层

decision_semantics.build_item_semantics()提供统一的语义映射，处理basic和exclusion规则的不对称性：
- Exclusion规则 + supports_conclusion=False → HIT, OPPOSE（发现风险）；
- Exclusion规则 + supports_conclusion=True → HIT, SUPPORT（无风险）；
- Basic规则 + supports_conclusion=True → HIT, SUPPORT；
- Basic规则 + supports_conclusion=False → HIT, OPPOSE。

#### 3.6.3 证据质量评分

每条证据在4个维度上评分（0-100）：
- 来源可靠性（30%权重）：政府来源=90，企业=70，个人=50，SQL成功=75；
- 时效性（20%）：2025-2026=95，2023-2024=75，2020-2022=50；
- 完整性（25%）：检查result_summary、sql、exec_status、result_raw、supports_conclusion；
- 相关性（25%）：成功+支持=95，无数据=40，失败=20。

#### 3.6.4 反事实推演

ConservativeArbiter.build_counterfactuals()方法为决定性证据生成"如果…会怎样"的反事实场景。对每条决定性证据，构造假设性反转（supports→contradicts或反之），检查结论是否改变。这为决策提供了因果敏感性分析，帮助识别"关键证据"。

#### 3.6.5 人工复核留痕

DecisionVerdict.requires_human_review标志在两种情况下置为True：
1. 规则引擎说PASS但加权投票说FAIL（确定性与LLM判断冲突）；
2. 第3层无明确多数（conclusion=MISSING）。

AdjudicationReport提供条款级结果：status、reason、evidence_refs、missing_fields、action_hint、evidence_score、clause_confidence及所有语义字段。next_actions部分生成具体的后续任务（补充材料、直接驳回、风险预警）。

DebatePersistence模块将完整会话数据（所有轮次、判断、证据、论证图、仲裁结果、裁决报告）保存到数据库，实现全流程可追溯。

### 4.2 核心模块实现

#### 4.2.1 Policy Pack加载器

PolicyPackLoader（`policy/policy_pack_loader.py`）扫描`policy_packs/`目录，解析每个子目录的6个YAML文件，构建PolicyPack对象。加载器同时提供legacy兼容层——`load_policy_configs_from_packs()`方法将新格式的PolicyPack转换为旧版PolicyConfig，确保平滑迁移。

#### 4.2.2 Schema Mapper

SchemaMapper（`data_sources/schema_mapper.py`）接收逻辑实体名，从Data Source Pack的schema_map.yaml中查找对应的物理表名和字段映射。支持字段级映射（如逻辑字段`id_card`→物理字段`sfzh`）和表级映射（如逻辑实体`person`→物理表`sys_user_info`）。

#### 4.2.3 Evidence Planner

EvidencePlanner（`cognition/evidence_planner.py`）的`plan()`方法实现从Policy Pack到EvidencePlan的转化。优先级排序确保basic_conditions最先执行。支持从Policy Pack自动加载和从legacy PolicyConfig兼容加载两种模式。

#### 4.2.4 Text2SQL Agent

Text2SQLAgent（`text2sql/dynamic/text2sql_agent.py`）的`generate_sql()`方法实现PlanItem到SQL的转化。模板优先策略（有sql_template则直接返回）减少LLM调用。QueryPromptBuilder构建约束性Prompt，DDLManager和DictManager提供表结构和数据字典支持。

#### 4.2.5 AutoDebugger

AutoDebugger（`text2sql/dynamic/auto_debugger.py`）实现三层修复流水线。`_enforce_detail_query()`方法对明细查询执行结构化守卫。错误反馈循环通过error_feedback参数将执行错误传递给LLM。

#### 4.2.6 ArgumentGraph

ArgumentGraph（`agents/debate_memory.py`）实现Dung论证框架。`compute_acceptable_set()`方法执行Grounded Semantics的迭代不动点计算。`summarize_conflicts()`方法生成结构化冲突摘要，用于注入后续轮次的Agent提示。

#### 4.2.7 AttackDetector

AttackDetector（`agents/attack_detector.py`）实现客观冲突检测。通过分析证据引用关系、立场对比、证据状态等信息，识别四类冲突，不依赖Agent自报的攻击目标。

#### 4.2.8 Unified Decision Engine

UnifiedDecisionEngine（`agents/unified_decision_engine.py`）实现三层级联决策。`decide()`方法按顺序执行规则引擎、加权投票、多数决，每层可独立运行和测试。DecisionVerdict封装完整的决策结果和元数据。

| 无修复基线 | 65.00% | 32.50% |
| Schema基线 | 62.50% | 37.50% |
| 有修复（本系统） | **87.50%** | **7.50%** |

SQL自诊断修复机制带来+22.50个百分点的匹配率提升和-25.00个百分点的警告率降低。

#### 5.1.3 多Agent消融实验

消融实验设计4种配置，验证多Agent辩论各组件的贡献：

关键发现：

- 从Pro-Con（80.56%）到Full（91.04%）的提升表明5角色设计和形式化论证框架的附加价值。

## 第6章 总结与展望

### 6.1 工作总结

本作品"智策通"是一个面向政策审查场景的多Agent智能研判系统，通过五大创新实现了从自然语言提问到可信决策输出的全链路自动化：

1. **可插拔政策包与数据源抽象架构**：通过Policy Pack和Data Source Pack双层插件体系，实现政策规则、数据源映射、采集器注册的完全解耦，新增政策或数据源无需修改核心引擎代码。三方解耦设计（"取什么"、"从哪取"、"怎么取"）是系统泛用性的基础保障。

2. **规则驱动的Text-to-SQL证据链**：五层证据链流水线（Evidence Planner → Text2SQL Agent → Prompt Builder → Evidence Assembler → Hard Rule Semantics）将政策规则自动转化为结构化查询，实现"规则→SQL→证据→结论"的端到端自动化。约束性Prompt设计和硬规则语义覆盖确保了查询的准确性和判断的确定性。

3. **SQL自诊断修复机制**：三层修复流水线（生成与安全替换、结构化守卫、错误反馈循环）将SQL查询首次执行匹配率从65.00%提升至87.50%，结构性警告率从32.50%降至7.50%，为后续多Agent辩论提供了高质量的证据基础。

4. **形式化论证框架驱动的多Agent辩论**：引入Dung抽象论证框架和ASPIC+攻击类型映射，设计5个具有不同认知视角的辩论Agent，通过客观冲突检测、举证责任三级分层、Grounded Semantics可接受集合计算，实现论证状态的形式化判定与动态收敛。完整多Agent辩论决策质量达91.04%，证据引用率达84.72%。

5. **三层级联决策引擎与人工复核留痕**："确定性规则引擎→加权投票→多数决"三层级联决策流水线，结合ConservativeArbiter反事实推演，实现决策结果的可解释性和人工复核的完整留痕。当各层判断冲突时自动标记人工复核需求，确保系统在不确定场景下的安全性。

### 6.2 未来展望

1. **SQL蒸馏小模型部署**：当前每次取证涉及20+次LLM调用，是主要延迟来源。计划采用DeepSeek-Coder-6.7B或Qwen2.5-Coder-7B进行领域蒸馏和量化部署，配合缓存层和批量化策略降低延迟和成本。

2. **多数据源并发采集**：当前证据采集为串行执行。计划引入异步并发采集机制，支持MySQL、API、文件等多种数据源的并行查询，提升取证效率。

3. **真实业务系统对接**：当前系统使用模拟数据。计划对接真实的就业登记、社保缴费等业务系统API，验证系统在真实数据环境下的可用性。

4. **偏好序论证框架扩展**：当前使用Dung的无偏好论证框架。计划引入Prakken & Sartor（2009）的偏好序扩展，支持论证之间的优先级排序，提升辩论结果的精细度。

5. **多策略并行支持**：当前系统一次只处理一个Policy Pack。计划支持多策略并行评估，实现"一人多策"的综合研判能力。
