# 面向政策资格认定的多智能体辩论式 Text-to-SQL 智能评审系统

## 1. 项目概述

本项目面向基层政务服务、社会保险补贴资格认定、政策主动服务筛查等场景，构建了一套“自然语言意图理解 + Text-to-SQL 自动取证 + 证据卡片结构化表达 + 多智能体辩论式裁决 + 可视化复核”的智能评审系统。

系统以政策资格认定为核心任务，将政策条款、数据库事实、SQL 查询结果、智能体判断过程和最终裁决报告统一组织起来。用户可以通过自然语言描述办理诉求或输入身份证号触发审查，系统自动识别适用政策，生成或执行取证 SQL，从业务数据库中抽取事实证据，再由多个角色智能体围绕政策条款和证据进行辩论、质询、复核与仲裁，最终形成具有证据引用、理由说明、风险提示和人工复核入口的评审结果。

项目重点解决传统政务资格审核中存在的几个问题：

1. 政策条款理解依赖人工经验，规则解释不稳定。
2. 业务数据分布在多张表中，人工核查成本高。
3. 大模型直接判断容易产生幻觉，缺少事实约束。
4. 单一智能体输出虽然简洁，但难以充分暴露争议点。
5. 自动化结论缺少可追溯证据链和人工复核闭环。

因此，本项目采用“数据库事实约束 + 多角色辩论 + 仲裁裁决”的架构，使大模型不直接凭空作出判断，而是在结构化 SQL 证据的约束下进行审查推理，从而提升系统的可靠性、可解释性和工程落地价值。

## 工程化快速入口

本仓库已补充本地开发和工程化约定，详见 [docs/development.md](docs/development.md)。

常用命令：

```powershell
# 后端配置
Copy-Item config\.env.example config\.env

# 后端依赖
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt

# 前端依赖
npm.cmd --prefix frontend install

# 启动
.\scripts\start-backend.ps1
.\scripts\start-frontend.ps1

# 测试
.\scripts\test-backend.ps1 -Mode unit
.\scripts\test-backend.ps1 -Mode api
.\scripts\test-frontend.ps1 -Mode all
```

敏感配置只允许写入 `config/.env` 或 `frontend/.env`，不要提交真实 API Key、数据库密码、虚拟环境、缓存、临时日志和本地 Agent 技能目录。

当前工程化改造已把政策与数据源拆成可插拔包：`policy_packs/` 保存独立政策定义，`data_source_packs/` 保存独立数据源定义。默认保留 `local_mysql_demo`，同时提供 `table_payload_demo`，用于在没有同步数据库时把客户系统、Excel 或表单 API 输出的结构化行直接转成证据卡片。

运行时取证计划已优先由政策包驱动：政策包声明“要取什么证”，数据源包声明“这些证据字段落在哪些表/资源”，collector 决定“怎么取”。提交前可运行 `.\scripts\validate-packs.ps1` 校验可插拔包契约。

## 2. 项目架构

### 2.1 总体架构

项目采用前后端分离的全栈结构，后端负责政策解析、意图识别、SQL 取证、多智能体辩论、裁决生成和历史会话持久化；前端负责用户交互、流式展示、证据卡片呈现、智能体观点可视化和人工补证复核。

整体链路如下：

```text
用户输入 / 身份证号 / 自然语言诉求
        │
        ▼
前端交互层 Vue + Element Plus
        │
        ▼
FastAPI 接口层
        │
        ├── 意图理解与政策路由
        │
        ├── 政策规则加载与条款结构化
        │
        ├── Text-to-SQL 取证链路
        │
        ├── 证据卡片装配与诊断
        │
        ├── 多智能体辩论审查
        │
        ├── 仲裁裁决与报告生成
        │
        └── 历史会话与人工复核持久化
        │
        ▼
MySQL 业务数据库 / 政策规则文件 / 评测样本
```

### 2.3 分层说明

#### 2.3.0 可插拔政策层

政策定义优先放在 `policy_packs/`，每个政策包独立声明 `manifest.yaml`、`rules.yaml`、`evidence_requirements.yaml`、`prompts.yaml` 和 `report_template.yaml`。当前 `flexible_employment_subsidy` 是第一个政策包，兼容旧运行时的 `POLICY_001`。

后端通过 `policy/policy_pack_loader.py` 加载政策包，并由 `policy/policy_router.py` 暴露成旧链路仍可使用的 `PolicyConfig`。因此新增政策时，优先新增政策包，而不是把规则写死进 Agent 或取证代码。

#### 2.3.0.1 可插拔数据源层

数据库映射优先放在 `data_source_packs/`，每个数据源包独立声明 `manifest.yaml`、`schema_map.yaml`、`collectors.yaml` 和 `connection.example.yaml`。当前 `local_mysql_demo` 是默认数据源包，对应现有本地 MySQL 样本库。

后端通过 `data_sources/loader.py` 加载数据源包，通过 `data_sources/schema_mapper.py` 解析逻辑实体与真实表字段。当前阶段已经支持 API 传入 `data_source_id` 并保留到运行结果、Trace 和持久化快照；SQL 执行入口由 `data_sources/session.py` 统一解析，目前支持 `mysql + config/.env` 数据源包。Collector 注册入口位于 `collectors/registry.py`，后续 Excel/API 数据源应通过独立 collector 接入。

#### 2.3.1 前端展示层

前端位于 `frontend/`，使用 Vue 3、Vite 和 Element Plus 构建。当前界面采用政务司法风格设计，通过红金配色、证据卡片、历史会话列表、智能体观点面板和裁决报告区域展示完整审查过程。

主要职责包括：

- 接收用户输入的身份证号或自然语言诉求。
- 展示政策识别和确认结果。
- 通过 Server-Sent Events 接收后端流式事件。
- 动态展示 SQL 取证结果、证据状态和诊断信息。
- 展示多轮智能体辩论过程。
- 展示最终仲裁结论、条款级结果和官方报告。
- 支持人工补证、人工复核和历史会话查看。

#### 2.3.2 API 接口层

API 层位于 `api/main.py`，使用 FastAPI 提供后端服务入口。该层负责接收前端请求，完成参数校验、政策解析、取证链路调用、辩论链路调用和结果返回。

主要接口能力包括：

- 发起资格审查。
- 发起流式资格审查。
- 自然语言意图理解。
- 获取政策条件。
- 查询历史会话列表。
- 获取历史会话详情。
- 提交人工复核确认。
- 生成或返回官方报告。

#### 2.3.3 意图理解与政策路由层

意图理解模块位于 `intent/`，政策路由模块位于 `policy/`。该层负责将用户自然语言请求映射到具体政策。

系统支持用户用自然语言表达需求，例如“我想申请灵活就业社保补贴”“帮我判断某个人是否符合企业社保补贴条件”。意图理解智能体会识别用户诉求中的业务对象、政策类别和需要确认的信息。当意图不明确时，系统会返回确认提示，避免误用政策规则。

#### 2.3.4 政策认知与规则层

政策相关文件分布在 `docs/policy/`、`policies/`、`policy/` 和 `cognition/` 中。系统将政策文本转化为结构化规则，包含基础条件、排除条件、补贴标准、计算逻辑和所需证据。

该层的目标是让政策规则从非结构化文本转变为机器可执行、可解释、可映射到数据库字段的结构化知识。

#### 2.3.5 Text-to-SQL 取证层

Text-to-SQL 相关代码位于 `text2sql/`。系统围绕政策条款和用户对象自动生成 SQL，查询数据库中的业务事实，并将结果转化为证据卡片。

该层包含：

- SQL 模板注册与规则映射。
- 动态 SQL 生成。
- 数据库 schema 认知。
- SQL 执行与结果采集。
- SQL 自动调试和修复。
- 查询结果与政策条款的证据装配。

与普通 Text-to-SQL 项目不同，本项目不是只追求生成一条 SQL，而是将 SQL 作为政策审查证据链的一环，重点关注“能否支撑最终资格认定”。

#### 2.3.6 证据模型层

证据模型位于 `evidence/`。系统将 SQL 查询结果封装为统一的 EvidenceItem / EvidenceBundle 结构，每条证据包含规则编号、目标人员、SQL 语句、查询结果、摘要、执行状态、诊断标签、置信度和是否支持结论等字段。

证据层使不同智能体共享同一组事实输入，避免每个智能体自行编造或重复查询数据。它也是系统可解释性的基础。

#### 2.3.7 多智能体辩论层

多智能体模块位于 `agents/`。系统设计了多个不同职责和视角的智能体，包括严格合规视角、宽松业务视角、审计复核视角、经验案例视角、探索补充视角和最终仲裁视角。

多智能体不是简单投票，而是围绕同一批证据和政策条款进行角色化审查。不同智能体可以提出支持、反对、待补充、风险提示等观点，系统再根据多轮辩论结果、证据引用情况、共识情况和冲突情况进行仲裁。

#### 2.3.8 持久化层

系统通过数据库保存辩论会话、轮次记录、证据结果和人工复核信息，使审查结果可以被追溯、复查和再次展示。持久化模块主要位于 `agents/debate_persistence.py` 和数据库相关配置中。

该层使系统从一次性 Demo 走向可查询、可留痕、可复核的业务系统。

#### 2.3.9 测试评估层

测试目录位于 `tests/`，覆盖 SQL 链路评测、多智能体链路评测、消融实验、证据采集测试、政策规则加载测试、语义包测试和提示词构造测试等。

测试层不仅用于验证代码正确性，也用于评估系统设计方案的有效性，例如对比是否启用 SQL 修复、是否启用证据约束、是否启用完整多智能体链路等。

## 3. 项目功能设计

### 3.1 自然语言诉求理解

系统支持用户用自然语言描述办理需求。意图理解模块会从用户输入中识别政策意图、目标业务和待确认条件。

功能设计重点包括：

- 支持自然语言政策咨询入口。
- 自动识别政策类型和业务场景。
- 在政策不明确时返回确认信息。
- 将确认后的政策 ID 传入后续审查链路。
- 降低用户对政策名称和系统操作的认知门槛。

### 3.2 政策条件展示与确认

当系统确定政策后，会提取该政策的结构化条件，并在前端展示基础条件、排除条件和补贴规则。用户可以在发起审查前理解系统将依据哪些条款进行判断。

该功能增强了审查过程的透明度，避免系统直接输出结论却不说明依据。

### 3.3 自动取证与 SQL 生成

系统围绕目标人员和政策条款执行取证。对于明确规则，可以通过 SQL 模板或动态 SQL 链路查询业务数据库；对于复杂场景，可以通过 schema 认知、字典映射和自动修复提升 SQL 可执行性。

该功能的核心价值是将人工查表、人工核验过程自动化，使政策资格认定建立在真实数据库结果之上。

### 3.4 证据卡片生成

每条 SQL 查询结果会被封装为证据卡片。证据卡片不仅包含原始查询结果，还包含面向审查任务的摘要和诊断信息。

证据卡片通常包括：

- 证据编号。
- 对应政策规则。
- 查询目标。
- 执行 SQL。
- 查询结果。
- 结果摘要。
- 执行状态。
- 是否支持当前结论。
- 异常诊断和人工复核建议。

证据卡片使后续智能体辩论不再依赖模糊上下文，而是基于结构化事实进行推理。

### 3.5 多角色智能体辩论

系统通过多个角色智能体对同一证据集进行审查。不同角色模拟政务审核中不同岗位或不同思维方式：

- 严格合规智能体关注政策条款是否被严格满足。
- 宽松业务智能体关注是否存在可解释的业务弹性。
- 审计智能体关注风险、异常和证据缺口。
- 经验案例智能体参考类似案例进行辅助判断。
- 探索智能体关注可能遗漏的信息和补证方向。
- 仲裁智能体整合争议并形成最终结论。

该设计能够缓解单智能体视角单一的问题，也能让系统显式暴露争议点和不确定性。

### 3.6 仲裁裁决与条款级结论

系统最终会生成仲裁结果，不仅给出“符合 / 不符合 / 待补充”等总体结论，还会对各政策条款进行条款级判断。

条款级结论包括：

- 条款是否满足。
- 支撑证据有哪些。
- 缺失字段或缺失证据是什么。
- 是否存在人工复核需求。
- 该条款对最终结论的影响程度。

这种设计使最终结论可解释、可审计、可追踪。

### 3.7 人工补证与复核闭环

当系统发现证据不足、字段缺失或结论存在争议时，可以触发人工补证流程。前端提供人工补充证据入口，用户可以针对具体条款补充说明或确认材料。

人工补证后，系统可以复用已有证据并重新发起审查，形成“机器初审 + 人工复核 + 再裁决”的闭环。

### 3.8 历史会话管理

系统支持保存并查看历史审查会话。历史记录能够展示过往人员、政策、证据、辩论过程、结论和复核状态。

该功能适合政务审核场景中的留痕要求，也方便项目展示时回放典型案例。

### 3.9 前端可视化展示

前端采用政务司法风格设计，围绕“可信审查”构建页面结构。主要可视化内容包括：

- 政策识别与条件展示。
- 人员画像和基础信息。
- 证据卡片列表。
- 智能体角色观点。
- 多轮辩论时间线。
- 仲裁结论与条款级报告。
- 人工复核面板。
- 历史会话列表。

前端不仅用于展示结果，也用于解释系统为什么得到该结果。

## 4. 项目系统设计

### 4.1 审查主流程设计

系统主流程可以概括为：

```text
输入诉求或身份证号
  → 意图识别与政策确认
  → 加载政策结构化规则
  → 根据规则规划取证问题
  → 生成或选择 SQL
  → 执行 SQL 获取业务事实
  → 组装证据卡片
  → 多智能体读取证据并输出判断
  → 多轮辩论与共识检测
  → 仲裁智能体生成最终裁决
  → 前端展示报告并保存历史会话
```

该流程强调先取证、后推理，避免直接让大模型凭经验生成资格结论。

### 4.2 数据流设计

系统的数据流由用户输入、政策数据、数据库事实、证据模型、智能体输出和裁决报告组成。

1. 用户输入进入 API 层。
2. 意图理解模块返回政策 ID 或确认需求。
3. 政策路由模块加载结构化政策规则。
4. Text-to-SQL 模块根据规则和目标人员查询数据库。
5. 查询结果被标准化为 EvidenceBundle。
6. EvidenceBundle 被传入多智能体辩论模块。
7. 每个智能体输出结构化 AgentJudgment。
8. 辩论编排器聚合多轮 AgentJudgment。
9. 仲裁器生成 ArbiterResult 和 AdjudicationReport。
10. 前端将证据、辩论、报告和历史记录可视化。

### 4.3 流式交互设计

为了提升用户体验，系统采用流式返回方式展示审查进度。后端在不同阶段向前端推送事件，前端逐步渲染。

典型事件包括：

- 开始审查。
- 完成政策识别。
- 完成证据采集。
- 输出某轮智能体判断。
- 输出仲裁结果。
- 输出最终报告。
- 审查结束或异常提示。

相比一次性返回完整结果，流式交互更适合多智能体系统，因为用户可以看到系统正在进行取证、讨论和裁决，而不是长时间等待黑盒结果。

### 4.4 证据约束设计

系统把证据作为智能体判断的输入边界。智能体的结论必须围绕证据卡片和政策条款展开，输出中需要引用规则或证据。

证据约束主要解决三个问题：

1. 降低大模型幻觉风险。
2. 保证结论可以追溯到数据库事实。
3. 让裁决过程具备可审计性。

消融实验也表明，缺少证据约束时，即使多个智能体形成共识，结论可靠性仍会显著下降。

### 4.5 多智能体协同设计

多智能体协同采用“角色分工 + 轮次辩论 + 共识检测 + 仲裁整合”的方式。

系统不简单依赖多数投票，而是综合考虑：

- 各智能体结论是否一致。
- 理由是否覆盖政策关键条件。
- 是否引用关键证据。
- 是否识别冲突和风险。
- 是否存在缺失数据。
- 是否需要人工补证。

这种设计更符合实际政务审核中的多人复核流程。

### 4.6 SQL 自动修复设计

Text-to-SQL 链路中加入了自动调试与修复机制。当首次 SQL 查询结果与预期不一致，或存在结构性问题时，系统可以触发重试修复。

修复机制关注：

- SQL 语法合法性。
- SQL 可执行性。
- 查询结果是否匹配期望。
- 是否出现多余过滤条件。
- 是否存在错误聚合或错误投影。
- 是否遗漏必要表连接。

测试结果显示，加入修复链路后，最终结果匹配率相比无修复链路有明显提升。

### 4.7 人工复核设计

系统承认自动化审查并不能完全替代人工判断，因此保留人工复核机制。当前端发现某条证据状态为待补充、字段缺失或争议较大时，用户可以通过人工补证面板提交补充材料。

人工复核信息会被转化为可复用证据项，并参与后续裁决，使系统具备人机协同能力。

### 4.8 前端主题与交互设计

前端采用“政务红 + 金色点缀 + 浅灰背景”的设计语言，视觉上贴合政策审查、司法裁决和公共服务场景。

界面设计目标包括：

- 用卡片呈现证据，降低信息密度。
- 用标签展示证据状态，提高可读性。
- 用多角色面板展示智能体观点，体现辩论过程。
- 用裁决报告突出最终结论和关键依据。
- 用历史列表支持结果回放。
- 用人工补证面板形成闭环。

## 5. 项目亮点设计

### 5.1 Text-to-SQL 与政策审查深度结合

项目不是孤立地做自然语言转 SQL，而是将 SQL 生成嵌入政策资格认定流程。SQL 查询结果会被进一步组织为证据，并用于多智能体审查和仲裁。

这种设计使 Text-to-SQL 从“查询工具”升级为“政策审查证据引擎”。

### 5.2 证据卡片机制提升可解释性

系统将数据库查询结果抽象为证据卡片，统一承载 SQL、结果、摘要、状态和诊断。前端和智能体都围绕证据卡片展开工作。

证据卡片机制带来的优势包括：

- 证据来源清楚。
- 智能体推理边界明确。
- 前端展示直观。
- 后续审计和复核方便。
- 可以定位缺失数据和异常查询。

### 5.3 多角色辩论增强决策质量

系统通过严格、宽松、审计、经验、探索、仲裁等不同角色模拟真实审核过程。与单一智能体相比，多角色辩论能提供更完整的理由、更高的证据引用率和更强的冲突识别能力。

消融实验表明，完整多智能体链路在综合决策质量、严格通过率、理由完整率和证据引用率上均优于简化方案。

### 5.4 证据约束抑制大模型幻觉

项目通过 SQL 取证和证据引用约束智能体输出。无证据约束实验显示，缺少证据时多智能体虽然可能形成共识，但结论准确率会大幅下降。

这说明本系统的核心不是简单叠加多个大模型角色，而是让所有角色在同一事实基础上讨论。

### 5.5 SQL 自动修复提升链路鲁棒性

系统设计了 SQL 生成后的执行验证和自动修复机制。评测结果显示，修复机制将最终结果匹配率从无修复链路的 65.00% 提升到 87.50%。

这说明在真实业务数据库场景中，仅依赖首次生成 SQL 不够稳定，执行反馈和自动修复是必要环节。

### 5.6 支持人工补证的人机协同闭环

对于证据缺失、字段异常、政策争议等情况，系统不会强行给出绝对结论，而是通过人工补证和复核机制将不确定性显式暴露出来。

这使系统更符合政务场景中“机器辅助、人工兜底、过程留痕”的应用要求。

### 5.7 面向比赛展示的完整可视化

项目具备较完整的前端演示能力，可以展示从输入、政策识别、取证、证据、辩论、仲裁到报告的全过程。相比只有后端脚本或单一模型调用的项目，本系统更容易向评委展示完整业务闭环和工程实现深度。

### 6.6 多智能体消融实验设计

多智能体评测用于验证不同智能体链路对政策判断质量的影响。实验包含四组：

| 测试组 | 测试内容 |
| --- | --- |
| Single Agent | 仅使用一个严格合规 Agent 根据 SQL 证据直接判断 |
| Pro-Con Debate | 使用严格合规 Agent 与宽松业务 Agent 进行正反辩论 |
| No Evidence Constraint | 保留多 Agent 数量，但隐藏证据卡片，测试无证据约束下的判断质量 |
| Full Multi-Agent | 完整链路：SQL 取证、证据卡片、多角色辩论、共识判断、仲裁裁决 |

评测指标包括结论准确率、综合决策质量分、严格通过率、理由完整率、平均证据引用率、共识率和冲突识别率。

综合决策质量分计算方式为：

```text
decision_quality_score =
0.35 * conclusion_correct
+ 0.25 * reason_complete
+ 0.20 * evidence_referenced
+ 0.10 * rule_coverage_pass
+ 0.10 * conflict_pass
```

该指标避免只看最终标签是否正确，更关注政务审查需要的理由完整性、证据引用、规则覆盖和冲突识别。

### 6.8 多智能体实验结论

从实验结果可以得出以下结论：

1. 完整多智能体链路综合效果最好。Full Multi-Agent 的综合决策质量分达到 91.04%，严格通过率达到 70.83%，理由完整率达到 91.67%，平均证据引用率达到 84.72%。
2. 正反辩论优于单智能体。Pro-Con Debate 相比 Single Agent，综合决策质量分从 80.83% 提升到 85.63%，严格通过率从 41.67% 提升到 54.17%。
3. 证据约束是系统可靠性的关键。No Evidence Constraint 的结论准确率只有 12.50%，平均证据引用率为 0.00%，说明脱离 SQL 证据后，多智能体结构本身并不能保证可靠判断。
4. 高共识不等于高质量。No Evidence Constraint 的共识率为 100.00%，但综合决策质量分只有 43.12%，说明共识必须建立在可靠证据基础上。
5. 完整链路不仅提高结论质量，还提高了可解释性。Full Multi-Agent 在理由完整率和证据引用率上均为最高，更符合政务审核中可追溯、可复核的要求。

### 6.9 测试结果总体说明

综合 SQL 链路评测和多智能体消融实验可以看出，本项目的关键设计均得到了实验支撑：

- Text-to-SQL 自动修复机制显著提升最终结果匹配率。
- 证据卡片机制是多智能体可靠判断的基础。
- 多角色辩论相比单智能体能提升理由完整性和综合决策质量。
- 完整的“SQL 取证 + 证据约束 + 多智能体辩论 + 仲裁裁决”链路相比简化方案更适合政策资格认定场景。
- 系统在保证自动化效率的同时，保留了人工复核入口，具备更好的实际应用可行性。

## 7. 项目总结

本项目围绕政策资格认定这一具有现实价值的政务场景，构建了从自然语言诉求到数据库取证、从多智能体辩论到可解释裁决、从自动审查到人工复核的完整系统闭环。

项目的核心创新在于没有让大模型直接替代人工审核，而是将大模型置于结构化政策规则和数据库证据的约束之下，通过 Text-to-SQL 提供事实基础，通过证据卡片组织审查材料，通过多智能体辩论提升理由充分性，通过仲裁报告形成可复核结论。

从测试结果看，SQL 自动修复、多智能体协同和证据约束均对系统质量有明显提升。该系统既具有计算机设计大赛所需要的技术综合性，也具有面向政务服务智能化、政策主动服务和辅助审核的应用价值。
